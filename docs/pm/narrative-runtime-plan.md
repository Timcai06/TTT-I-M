## 目标与范围

从章节各自决定世界状态，逐步转为：语义故事位置 → 完整基础状态 → 场景绑定 → 最终相机 → 统一投影 → DOM/WebGL/后续音频表现。

首个完整验证样段采用 **About → Life → Frame**，包括阅读、收回、物件转移、进入、反向及直接定位。既有房间 → About 入口作为回归边界保留；首轮不同时做全站美术改版、手机 3D、Studio、音效库或 Blender 重建。

成败以实际体验与真实场景状态衡量，不以新增模块数量衡量。

## 建议确认的架构原则

1. **语义位置唯一**：`segment + progress` 是权威位置；全局 `time` 由故事顺序和权重推导，不再独立存储第三份可写状态。布局版本负责映射，不定义故事。
2. **基础状态完整**：同一故事/内容/资产版本、位置及显式用户状态 U 得到相同基础世界。会话播放历史不得偷偷参与；哪些物件保持或收回由叙事规则明确。
3. **状态类型分开**：叙事状态、输入/惯性等短期状态、用户持久选择和瞬态事件分别管理。确定性检查关闭短期偏移，或提供同样输入序列。
4. **同帧单一写入者**：受控属性先绑定物体并更新矩阵，再求最终相机、投影、表现与绘制。新旧路径过渡期间同一属性仅一个写入者。
5. **内容身份与载体分开**：稳定对象 ID 绑定资产与裁切；多个视觉代理的归属和交接权重明确，交互所有者唯一。视觉重合期间允许受控双载体，不允许两份独立照片同时残留。
6. **已有能力继续使用**：扩展现有 NarrativeSpec；复用 GPU/资源/恢复/投影安全处理、常驻舞台、真实章节内容及声音偏好基础设施。
7. **统一调度有范围**：统一主空间叙事的更新入口与顺序，保持静止时按需绘制。章节独立效果只在确实消费空间快照时接入，不顺手重写所有 rAF、GSAP 和 shader。
8. **分阶段替换**：类型草案先最小化；旧入口可作为转换适配器，但不得根据 shot 再决定第二套世界。每轮有明确切换点、回退路径和删除清单。

样段中的照片身份由 ARCH 核对实际素材与物件后列明：Life 内容、Frame 入口和 Frame → Stack 收尾图不能仅因都称“照片”就合并成一个 ID；需要连续的交接逐条定义源、目标、资产和裁切，涉及替换真实图片须交 PM/tim 决策。

建议 StoryFrame 包含基础世界、相机意图与表现意图；提交快照另带 frameId、layoutVersion、最终相机和资源代次。具体名称及字段以 ARCH 的最小接口合同为准，不提前创建空模块树。

## 迁移期间如何保持可用

- 先影子采样并比对状态，再接管样段的完整写入域；影子阶段不得驱动第二个世界或触发声音。
- 样段与旧章节切换时，各路径绝对应用本域需要的状态，不能依赖对方遗留姿态。每个旧、新边界明确重置/保持清单。
- `withSession/remember` 等历史记忆不能直接删除。先列出它服务的产品语义：能由故事推导的迁走；属于用户选择的显式化；不再需要的才移除。
- 暂时的 inert 阅读快照不等于新建第二棵交互 React 树。当前快照支撑任意阅读位置返回，在替代方案覆盖这一能力前保留；不能以“禁止克隆”为由退回章节首屏。
- 模型节点与 clip 绑定缺失必须在准备阶段报告并走既有可读降级；关键绑定不得静默跳过，也不将任何缺失都变成全站白屏。
- 精确接口可在样段后修订；不要把输入中的示例段落列表直接变成新增 DOM section，也不要为三份合同强行复制现有内容事实。

## 验收矩阵

| 层次 | 检查 | 不可替代的证据 |
| --- | --- | --- |
| 纯采样 | 相同版本、T、U 得到相同基础状态；段前/中/后和边界定义完整 | 固定位置用例，不能只比较自身输出与自身 |
| 真实绑定 | 新加载模型直接定位 T，与多次正反/跳转后再定位 T 比较 | 所有受控变换、可见性、动画权重、材质状态的实际读回；容差按属性在执行前定义 |
| 同帧配准 | 物体、最终相机、DOM 使用同一 frameId/layoutVersion/资源代次 | 提交轨迹及实际矩阵读回，单靠字段相等不足以证明顺序正确 |
| 内容交接 | 图片 ID、裁切、四角、颜色及交互归属一致 | 真实内容/物件检查，正滚、反滚、停驻、快跳；tim 判断视觉质量 |
| 布局与恢复 | 字体/图片/resize 后定位；GPU 重建；旧事务取消 | 当前语义位置和最终提交状态；不混合多个布局版本 |
| 稳定性 | 无重复上下文/持续重渲染回归；资源不可用仍可读 | 相同设备、视口、DPR、版本下的按需绘制与必要性能记录 |
| 音频（后期） | seek 不补播、方向/去重/偏好正确 | 事件日志及实际播放检查；render 提交不冒充显示器呈现确认 |

只做与变更相关的必要测试；不建立自动美术评分门禁，不要求不同 GPU 像素一致。自动化证明功能范围，tim 判断最终画面和节奏。

## 会话与确认方式

固定名称采用 **PM / ARCH / DEV / QA**；**ART** 在精修时按需启用，声音先由 DEV 接任务，不另常驻一个会话。

- PM：本会话，不需要新建。
- ARCH：一次性解决架构高不确定性，接口明确后停止；开发发现跨层问题再唤起。
- DEV：同一时间唯一产品代码写入者，任务卡按需切换模型。
- QA：验收会话，复核事实与功能；不修产品代码，不代替 tim 美术验收。
- ART：只设计可观察的精修方案，实施仍由 DEV 按卡片完成。

开工提示词见 [会话初始化说明](sessions/README.md)。现在粘贴提示词仅初始化角色并读取当前计划；没有用户确认和 PM READY 任务卡，不开始开发。

建议 tim 确认的计划重点：以当前本地实现为基线、About → Life → Frame 为首段、先确定性与同帧交接再全局迁移、四个核心会话按需工作。方案获确认后，由 ARCH 接 NR-00 规划卡，PM 据回报生成首张开发卡。
