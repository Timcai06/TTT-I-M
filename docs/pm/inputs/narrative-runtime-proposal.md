# 一、先明确：源码里真正需要改变的是什么

目前空间叙事的主要调用链是：

```text
ArchiveChapterBridge
  创建自己的 ScrollTrigger
  更新自己的 ArchiveProgress
           ↓
PersonalArchiveSurface
  根据 visible 挂接当前章节
           ↓
archiveRuntime.attach(...)
  设置当前 active shot
  将共享 Canvas 放进当前 host
           ↓
archiveRuntime.draw(...)
  director.pose(shot, progress, page)
  sheet.update(...)
  composer.render()
```

这条链路已经实现了“章节适配器”和“共享渲染资源”的分离，并不是每个章节重新创建一个 Three.js 世界。这个基础应该保留。

但从下一阶段的目标看，我认为有六个边界需要重新划分：

| 当前源码 | 我看到的限制 | 我会调整成 |
|---|---|---|
| `ArchiveChapterBridge` 自己创建进度并编排表现 | 每个桥接拥有一部分故事解释权 | 章节提供布局锚点，统一运行时解释故事位置 |
| `archiveDirector.pose(shot, p, page)` | 同时处理动画、相机、可见性、DOM | 世界绑定、相机求解、DOM 表现分开 |
| `chapterTracks.ts` | 镜头参数、目标章节、阅读节奏混在一起 | 明确的叙事段落与属性轨道 |
| `archiveRuntime.attach()` | 当前挂接的章节决定当前世界输入 | 世界持久存在，章节只注册表现目标 |
| `archiveReadingSurface` | About 使用真实 DOM，其他段落主要重绘标题 | 按内容身份交接，针对不同内容选择表现方式 |
| `SoundProvider` | 以 SciScope 配乐切片为主要模型 | 保留音频基础设施，增加声场状态与交互事件两条路径 |

这些不是根据目录名称推测：当前 `pose()` 确实会修改相机、GLTF 动画、显示器可见性和 `page.style`；阅读面也确实区分了真实 About DOM 与其他镜头的 Canvas 标题纹理；声音则明确使用 `entry/query/evidence/synthesis` 四段配乐。

**因此，我的第一刀不是换技术栈，也不是先把 Canvas 改成 fixed，而是把“谁决定当前状态”这件事收回到一个地方。**

# 二、总体架构：把“故事”“运行”“表现”分成三层

我会采用下面的结构：

```text
作者配置
Story Graph + 叙事对象身份 + 场景绑定合同
                    │
                    ▼
              叙事内核
       sampleStory(storyPosition)
                    │
               StoryFrame
                    │
                    ▼
              帧协调器
   输入 / 生命周期 / 布局版本 / 资源就绪
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
  Scene Binding  Camera Rig   Interaction
       │            │            │
       └────────────┼────────────┘
                    ▼
          同一帧的几何与投影快照
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   WebGL 表现     DOM 表现     Audio 表现
```

这里有一个非常重要的区别：

**叙事内核决定“发生了什么”，表现适配器决定“怎么把它画出来、播放出来”。**

例如：

```text
故事事实：
这张照片已经从生活记录进入摄影档案。

表现方式：
桌面端：照片在 3D 空间中移动，再交接到 DOM。
低性能端：保留照片身份，使用简化转场。
减少动态效果：直接进入可阅读的摄影档案。
```

三者的运动方式可以不同，但不应该出现不同的内容、不同的对象身份，或者不同的最终世界状态。

同时，我不会把这三层都放进 React Context。

我会让 React 管理章节内容、导航、菜单、偏好和资源状态；让帧运行时管理相机矩阵、物体姿态、Shader 参数和投影坐标。React 只订阅需要界面重渲染的离散变化，而不是每一帧接收整个 `WorldState`。

# 三、`StoryClock` 不是一个 `scrollY / totalHeight`

附件提出统一的 `StoryTime`，这个方向我同意。但直接加一个：

```ts
const t = scrollY / (documentHeight - viewportHeight)
```

并不能解决问题。

**我会让故事先有稳定的语义位置，再映射到滚动位置。**

## 1. 故事位置与布局位置分开

建议的接口大致是：

```ts
interface StoryPosition {
  segment: SegmentId
  progress: number
  time: number
}

interface ScrollSpan {
  segment: SegmentId
  start: number
  end: number
  layoutVersion: number
}
```

例如：

```text
StoryPosition:
  segment = life-frame
  progress = 0.63

Desktop ScrollSpan:
  start = 当前布局中这段故事的起点
  end   = 当前布局中这段故事的终点
```

`time` 是整个故事中的归一化坐标，但它应该由**段落顺序、作者权重和局部进度**推导出来，而不是把某次页面高度当作故事定义。

这样，图片解码、字体加载、窗口尺寸变化后，系统仍然知道：

> 用户正在 `life-frame` 的 63%，而不是只知道用户在第 8,421 个像素。

## 2. 导航章节不等于故事段落

当前 `narrativeChapters.ts` 是从导航和进度条集合推导出来的，因此 `life`、`work-transition` 被刻意排除。这对导航高亮是一个明确选择，但不适合作为完整故事运行时的拓扑。

我会保留现有导航集合，同时另建完整的叙事集合：

```text
导航：
HOME / ABOUT / FRAME / STACK / WORK / CONTACT

故事：
hero
hero-about
about-reading
about-life
life-reading
life-frame
frame-reading
frame-stack
stack-reading
stack-work
work-reading
work-contact
contact
```

这只是目标语义示例，实际段落数量应依据现有桥接和阅读区间整理，不应机械地再增加一套 DOM Section。

还有一点：仓库已经存在 `core/narrative/types.ts` 和 `specs.ts`，并且有 `defineNarrativeSpec()`、阶段范围验证及 Work Transition 的配置。我会从这里扩展，而不是完全另起一个不兼容的叙事配置系统。

## 3. 跳转必须成为一次定位事务

当前 `App.tsx` 在深链接跳转后，会通过 `120 / 520 / 1100ms` 三次延迟再次校正位置。这说明现有系统已经在处理“布局晚到、定位失效”的实际问题。

我会将它收束成：

```text
请求目标故事位置
       ↓
确认目标内容与布局锚点可用
       ↓
刷新并提交新的 ScrollMap
       ↓
将语义位置换算成滚动位置
       ↓
立即求出目标世界状态
       ↓
提交目标帧或可用的 DOM 降级状态
       ↓
完成跳转
```

每次定位有自己的请求编号。新的跳转、用户主动滚动、组件释放，都能取消旧请求。

布局继续变化时，依据布局版本重新定位，而不是长期依赖几组时间常数猜测布局是否已经稳定。

**正常滚动时，StoryClock 消费实际平滑后的滚动位置；不要再给故事时间叠一层缓动，让世界比 Lenis 又慢半拍。**

# 四、最重要的一刀：把 `archiveDirector` 改成“完整状态求解 + 明确执行”

## 1. 当前问题不是不会 seek，而是 seek 的单位仍然是镜头

当前代码里有这样的逻辑：

```ts
name.startsWith('Life')
  ? shot === 'about-life'
    ? phase(progress, .23, .62)
    : shot === 'life-frame'
      ? chapter.picture
      : 0
```

意味着到了其他镜头，Life 对应动画量会回到 `0`。`FramePrint` 等通道也存在按当前镜头决定取值的逻辑。与此同时，Notebook 在非 entry 镜头保持打开，说明源码其实已经有部分跨镜头状态延续。

因此，我不会简单宣布“所有归零都是 bug”。

真正的问题是：

> **哪些东西应该保持，哪些东西应该收回，哪些东西只是换了表现载体，目前主要藏在镜头判断里，没有完整的世界语义。**

## 2. 世界状态不等于所有动画进度都停在 1

这是我会对附件方案进一步精确化的地方。

例如照片从信封进入照片墙后：

```text
Notebook：仍然打开。
Envelope：可以保持打开。
Photo：现在属于照片墙。
Life 中的照片代理：不再显示。
Frame 中的照片代理：接管显示。
```

不能只是：

```text
photoExtracted = 1
framePrintVisible = 1
```

否则可能同时留下两张照片。

所以我会让世界状态表达**叙事事实**，再由场景绑定决定具体动画与可见性：

```ts
interface StoryFrame {
  position: StoryPosition

  world: {
    notebookOpen: number
    envelopeOpen: number

    photo: {
      id: NarrativeObjectId
      placement: 'envelope' | 'transfer' | 'rail'
      transfer: number
    }

    drawerOpen: number
    folderLift: number
    monitorMode: 'photo' | 'project'
  }

  camera: CameraIntent
  presentation: PresentationIntent
}
```

这里的名字是建议接口，不是声称当前 GLB 已有这些节点。

## 3. 把 `pose()` 拆成三个责任

我建议最终形成：

```ts
const storyFrame = sampleStory(position, storyDefinition)

sceneBindings.apply(storyFrame.world)
cameraRig.solve(storyFrame.camera, viewport)
surfacePresenter.apply(storyFrame.presentation, projection)
```

职责分别是：

**`sampleStory()`：决定状态。**<br>
它不访问 DOM，不直接修改 Three.js 对象，不依赖上一次播放到哪里。每个被运行时控制的属性，在整个故事区间都有定义，包括动作之前、动作之中和动作之后。

**`sceneBindings`：把语义状态写入模型。**<br>
负责 GLTF 动画采样、物体变换、显示器模式、可见性和材质绑定。

**`cameraRig`：根据镜头意图求解相机。**<br>
负责空间路径、观察目标、构图、视场角、对焦和必要的次级偏移。

当前 `pose()` 最后还会写 `page.style.transform` 和 `opacity`，这一部分应彻底移出 Director。它不应该知道 HTML 页面如何显示。

## 4. 动画绑定不能继续只依靠正则和隐藏时间区间

当前 Director 根据动画名称正则选取 clip，并且在代码中包含 `[1, 2.4]`、`[74 / 30, 110 / 30]` 等片段范围；找不到 action 时会直接返回。

我会把这些变成可验证的绑定定义：

```text
语义属性 → Clip → 有效时间区间 → 控制节点 → 混合规则
```

加载时就验证关键 clip 和节点是否存在，而不是滚动到中途才发现某个动作没发生。

另外，**统一故事时间，不代表所有 AnimationAction 都写同一个时间值**。Three.js 本身区分 Mixer 全局时间与 Action 局部时间、权重和混合方式；这些应由绑定层明确处理。

我还会检查不同 clip 是否同时控制相同属性。这里尚未逐轨检查 GLB，所以不能断言当前已经存在混合冲突；但它应该成为新绑定层的检查项。

# 五、相机设计：从“在两个点之间移动”变成“围绕叙事对象构图”

当前相机已经做了不少事情：在 `views` 之间插值、加弧线偏移、根据阅读面法线接近目标，以及为 Life 照片绕开架子增加专门的偏移。这些都说明问题不是“缺一个相机动画库”。

我会保留这些已有结果，但改变参数组织方式。

## 镜头首先描述观看目的

例如：

```text
life-frame

主角：正在转移的照片
出发构图：照片与信封仍能同时辨认
移动过程：保持照片可追踪
到达构图：照片与墙面目标重合
交接构图：照片内容区与 DOM 内容区重合
```

然后再落到：

```text
position path
look-at target
FOV
subject screen position
safe area
focus distance
```

这里的重点是：**相机不是自己表演，它要帮助用户持续辨认同一个对象。**

## 相邻镜头必须共享边界状态

我会要求：

```text
上一段结束的相机状态
          =
下一段开始的相机状态
```

但还不够。

对于不停顿的连续运动，还要检查边界速度方向是否连续；对于阅读停留，则应该明确设计成自然停稳，再启动下一段。

不要只检查 `views.life` 是否相同，因为当前镜头结束时可能已经经过了 `approach` 和阅读面求解，实际相机位置不再等于最初定义的 View。

## 次级惯性不能破坏配准

后期可以加轻微的鼠标视差、速度响应和相机惯性，但：

> **DOM 投影和 Audio Listener 必须使用加入次级偏移之后的最终相机。**

否则相机微微动了，贴在纸上的文字没动，用户会立刻看出两层系统在各自运行。

# 六、统一帧调度：比“统一状态对象”更重要

目前 Lenis 在 GSAP ticker 中推进；章节测量通过自己的 rAF 合并更新；Archive Runtime 也有按需 rAF 绘制。这些各自有合理目的，但对于严格的空间配准，需要把主叙事的更新顺序显式化。

我不会再额外创建一个永远运行的新循环。

正常模式可以继续使用 GSAP ticker 作为驱动入口，将现有 Lenis 推进与主叙事更新纳入明确的执行顺序。GSAP 官方也提供 ticker 回调和优先级机制，但实际接入时仍应显式安排调用链，不能只靠多个模块碰巧按正确顺序注册。

建议的帧流程是：

```text
① 推进滚动驱动，取得实际位置
② 读取已提交的布局版本
③ 计算 StoryPosition
④ 采样完整 StoryFrame
⑤ 应用 GLTF 动画与物体状态
⑥ 更新世界矩阵，求出交接对象位置
⑦ 求解最终相机
⑧ 计算统一屏幕投影
⑨ 写入 DOM / Shader / 音频混合目标
⑩ 提交 WebGL 绘制
⑪ 处理本帧允许触发的瞬态事件
```

其中有三个硬约束。

**第一，先更新物体，再求相机，再投影。**<br>
不能拿上一帧的模型矩阵投影这一帧的文字。

**第二，同一帧的消费者使用同一份快照。**<br>
快照至少带有 `frameId`、`storyPosition`、`layoutVersion` 和最终相机信息。异步资源准备完成后，只能使下一帧失效重算，不能在提交一半时偷偷更换当前目标。

**第三，统一调度不等于持续满帧渲染。**<br>
世界静止、没有次级运动、没有需要刷新的材质时，应继续保持按需绘制；不要为了“世界一直存在”，让整页始终跑重后处理。

## 布局测量也要有边界

当前 `chapterScrollMetrics` 已经将布局读取集中起来，但仍会在更新快照时读取注册章节的 DOMRect。

我会继续保留集中测量，把它逐步分成：

```text
布局变更：
更新段落范围、阅读目标矩形、viewport 等。

普通滚动：
优先使用缓存范围 + 当前滚动位置计算。
```

涉及 pinned section 的范围，应使用刷新完成后的测量结果，不能机械地把所有区间改成 `offsetTop`。

# 七、Handoff 的设计核心：身份、载体、配准

这一部分直接决定你想要的“连贯感”。

## 1. 内容身份必须显式，不能依靠数组位置

源码已经有值得保留的实现：

```ts
const image =
  archiveThemes.at(-1)?.clusters.at(-1)?.slots[0]?.image
```

这张收尾图片会被贴到显示器对应的物理表面上。也就是说，你已经开始做“同一内容跨媒介延续”，并非所有过渡都是假的。问题是它目前依赖数组末项。

我会改成显式绑定：

```text
frame-to-stack 的交接对象
          ↓
一个稳定的 NarrativeObjectId
          ↓
对应图片资产、裁切信息、内容记录
```

内容顺序变化，不应该悄悄更换承担叙事任务的图片。

## 2. 同一个对象允许多个载体，但只能有明确的表现归属

例如同一张照片可以有：

```text
GLB 中的照片网格
转移阶段的独立网格
Frame 中的真实 DOM 图片
```

但我会定义一个连续的交接状态：

```text
物理对象显示
    ↓
物理对象与目标 DOM 精确对齐
    ↓
在重合区间完成表现切换
    ↓
真实 DOM 接管阅读和交互
```

重点不是禁止所有 crossfade，而是：

> **切换的是表现载体，不是内容身份；crossfade 不能用来掩盖位置、裁切和对象不一致。**

交接验证应该包括图片资源、裁切区域、内容区四角、纸边比例和颜色处理。不能只保证两个容器大小接近，因为容器边界不一定就是图片内容边界。

## 3. 不能靠 `onComplete()` 决定照片最后属于哪里

我不会这样设计：

```text
动画结束回调
    ↓
把照片挂到另一个 parent
    ↓
以后就认为照片在墙上
```

因为从中途直接进入时，回调没有发生。

我会让照片在任意 `T` 的位置，都能由源锚点、目标锚点和交接进度求出。节点层级只是实现手段，不是故事真相。

## 4. 投影层要从 About 的实现扩展，而不是重新造

当前 About 已经使用投影四角构建 `matrix3d`；`pageProjection.ts` 还检查非有限值、折叠/侧向四边形和退化情况。这些应保留并抽成统一投影服务。

我建议投影结果不只返回 `x/y`，还应提供：

```text
内容四角
深度与近裁剪状态
平面是否适合展示
屏幕包围范围
当前 viewport / frame 版本
```

同时要明确：**投影落在屏幕内，不等于没有被其他物体遮挡。**

初期可以通过经过设计的交接镜头保证平面可见；以后再增加必要的遮挡判断，而不是第一轮就构建复杂的通用 DOM–WebGL 深度合成系统。

对于 About，继续优先真实 DOM。对于照片，使用共享图片资产。对于项目封面，使用同一内容模型。**我不会把所有章节截图成纹理，也不会复制整棵带有交互状态的 React DOM。**

# 八、场景合同要扩展，但不能成为另一个大杂烩

当前 `scene-contract.json` 已经包含 `sourceSha256`、`coordinateSystem`、Views、Surfaces 和 Monitor States。

我会将相关配置分成三个合同，而不是全部塞进同一个 JSON。

| 合同 | 负责什么 | 不负责什么 |
|---|---|---|
| 场景合同 | 模型节点、坐标系、锚点、表面、动画绑定、资源指纹 | 哪个项目排第一、哪一章播放什么故事 |
| 内容身份合同 | 照片、项目、封面、裁切、叙事对象 ID | 相机如何绕行 |
| 叙事合同 | 段落、轨道、交接、镜头意图、声音提示 | Three.js 对象实例和 DOM 节点 |

这样 Blender 负责空间事实，内容层负责内容事实，故事配置负责艺术编排。

加载场景时建立一次索引并验证关键绑定。不要在每一帧反复 `getObjectByName()` 寻找同一批节点，也不要在热路径不断创建临时四角数组和向量。当前阅读面更新中就有可进一步缓存的节点查找与临时对象创建。

但我不会为了这点优化先全面拆文件。**先确定状态所有权，再优化热路径，顺序不能反过来。**

---

# 九、固定 `WorldCanvas` 是最终形态，但不应成为第一步

当前 `archiveRuntime` 已经处理了不少难题：共享资源加载、纹理准备、实际镜头变体预热、HDR 非有限值处理、Context Lost 恢复、质量档位和释放逻辑。迁移时应尽量保留这些，而不是重写一套“更干净”的 Renderer，丢掉已有防护。

我最终会让应用结构接近：

```tsx
<ExperienceRoot>
  <WorldCanvas />

  <main>
    <StoryChapters />
  </main>

  <Navigation />
  <TransitionOverlay />
</ExperienceRoot>
```

但顺序是：

```text
先统一状态输入
       ↓
再让所有章节消费统一帧
       ↓
最后将 Canvas 固定挂载
```

到那时，`attach(host, page, shot, progress, events)` 不再负责“切换世界”，而会拆成：

```text
世界挂载：由 WorldCanvas 唯一负责。

DOM 表面注册：由章节注册阅读目标。

可见性与资源需求：章节报告需求，运行时统一决策。
```

章节卸载不能销毁整个世界；世界渲染失败也不能让正文不可读。

另外，当前 `archiveEnabled()` 明确在窄屏和减少动态效果模式下关闭 Archive。我不会把桌面 Runtime 重构同时变成“强行开放手机 3D”。第一轮继续保留这条降级边界，后续再单独设计移动构图与预算。

# 十、交互与声音：需要统一原因，但不能全部塞进 `f(T)`

这里必须把附件里的目标进一步分清。

## 1. 三类状态不能混为一谈

| 类型 | 例子 | 能否仅由 `T` 重建 |
|---|---|---|
| 叙事状态 | 抽屉开度、照片位置、基础相机、阅读阶段 | 应当可以 |
| 瞬时交互状态 | 鼠标偏移、滚动速度、惯性残留、按压 | 不可以，还需要输入与时间 |
| 离散事件 | 夹子扣合声、按钮点击、抽屉碰撞声 | 需要判断是否发生跨越或操作 |

因此，我会使用：

```text
基础世界 = sampleStory(T)

交互响应 = updateInteraction(input, dt)

最终表现 = compose(基础世界, 交互响应)
```

这样才能同时保留“任意定位”和“有生命感”。

如果后续允许用户真正改变照片选择、灯的开关、抽屉内容，那是明确的用户状态 `U`，世界应写成 `World = f(T, U)`，不能偷偷依赖之前某个回调有没有执行。

## 2. Shared Cause 不是把所有参数绑定到同一个速度值

我会统一采集滚动速度、方向、指针和按压信号，但每种表现有自己的作用区间与响应曲线。

例如：

```text
同一次快速滚动
       ↓
照片纸边出现轻微运动
相机产生有限的运动偏移
转移声音纹理增强
```

不应该变成：

```text
快速滚动 → 全站所有东西一起扭曲、抖动、变色
```

阅读区间尤其需要收敛。明确的交接区间可以更强，正文阅读阶段则让视觉与声场安静下来。

## 3. 声音分“持续声场”和“一次性事件”

现有 `SoundProvider` 中的偏好管理、AudioContext 激活、资源取消、淡出、页面隐藏处理和 Film Mode 值得保留。新的 AudioDirector 应接入这些能力，而不是创建第二套互不协调的音频系统。

我会设计两条路径：

```text
持续声场：
StoryFrame + 最终相机 + 交互强度
              ↓
环境音与空间声源的混合目标

一次性声音：
故事区间跨越 / 用户操作
              ↓
方向判断 + 去重 + 就绪检查
              ↓
允许播放的事件
```

直接跳到 Work，应该恢复 Work 所需的声场，**但不应该补播前面所有翻纸、夹子和抽屉声音**。

反向滚动也不应该默认把所有声音倒放。每类事件可以选择静默、专门的反向声音，或者在重新经过触发区间时再允许播放。

空间音频还有一个需要落实准确的细节：**相机对应 Listener，物体声源对应 PannerNode**。Listener 的位置和朝向使用最终相机结果；不是把相机当作一个 PannerNode。

## 4. “画面同步”不能写成虚假的强保证

我赞成附件中“不使用随意的 `setTimeout` 给画面配音”的目标。

但我会区分：

```text
这一帧已经提交绘制
```

和：

```text
显示设备已经真实显示这一帧
```

设计上先保证声音不会早于相关状态与资源准备完成，并在提交绘制后放行事件；精细同步再考虑音频时钟与输出时间估计。Web Audio 提供 `getOutputTimestamp()` 关联音频输出时间与 performance 时间，但不等于获得了显示器呈现确认。

所以验收应写成可测的视听同步预算，而不是在 `composer.render()` 后发一个名叫 `actuallyPresented` 的事件，就宣称绝对同步。

# 十一、我会怎样实际落到代码和 PR

我不会第一天新建几十个模块。开始时只建立必要边界，目录大致这样：

```text
src/
├─ core/
│  ├─ narrative/
│  │  ├─ types.ts            扩展现有定义
│  │  ├─ specs.ts            保留现有配置入口
│  │  ├─ storyGraph.ts       完整故事拓扑
│  │  └─ sampleStory.ts      纯状态采样
│  │
│  └─ experience/
│     ├─ runtime.ts         帧协调与生命周期
│     ├─ storyClock.ts       唯一故事位置
│     ├─ scrollMap.ts        布局与故事的映射
│     └─ signals.ts          共享交互输入
│
├─ components/personal-archive/
│  ├─ archiveRuntime.ts      保留 GPU 与资源基础
│  ├─ sceneBindings.ts       模型绑定与绝对状态应用
│  ├─ cameraRig.ts           相机构图与路径
│  ├─ surfacePresenter.ts    投影与表现交接
│  └─ WorldCanvas.tsx        后续迁移固定挂载
│
├─ content/
│  └─ narrativeObjects.ts    显式内容身份
│
└─ lib/sound/
   ├─ SoundProvider.tsx      保留用户与设备侧能力
   └─ audioDirector.ts       声场与事件适配
```

其中旧 `archiveDirector` 在迁移期间可以作为兼容入口存在，但最终不能继续一边接收全局世界状态，一边按 `shot` 自己重新决定另一套状态。

## 迁移顺序

| 阶段 | 改什么 | 必须拿到的结果 |
|---|---|---|
| **第一轮：确定性内核** | 扩展 NarrativeSpec；新增故事采样；拆出场景绑定；先保持现有挂载方式 | 直接定位与顺序滚动得到一致的基础世界 |
| **第二轮：一个完整交接** | 打通 About → Life → Frame；建立照片身份、锚点和表现归属 | 正滚、反滚、直接进入都能保持对象连续 |
| **第三轮：统一帧与世界挂载** | 收束主叙事调度；移除桥接局部状态所有权；固定 Canvas | 相机、物体、DOM 使用同一帧；资源恢复后状态正确 |
| **第四轮：表现精修与声音** | 调整镜头曲线、次级响应、材质和 AudioDirector | 在已稳定的基础上改善节奏与质感，而不是继续补同步问题 |

第一轮不应该同时做材质升级、重写所有 Shader、移动端全量 3D、完整音效库。

不是这些不重要，而是它们应该建立在可验证的叙事基础上。

## 验收不能只测 `sampleStory()`

附件提出“直接跳到任意 `T`，不播放前面的动画，也能重建世界”，我会把它作为核心验收条件。

但必须测两层。

**纯状态层：**相同的故事版本、内容版本和位置，应得到相同的基础状态。

**真实场景层：**一个刚加载的模型直接应用 `T`，与另一个经历多次前进、后退、切换后再应用 `T` 的模型，其受控变换、可见性、动画权重和材质状态应在规定误差内一致。

否则，纯函数测试全部通过，也可能掩盖 Three.js 绑定层残留的历史状态。

此外，我会重点验收四类情形：段落边界前后是否跳变；布局刷新后是否仍在同一语义位置；GPU 恢复后是否能重建当前世界；seek 和反向滚动是否误触发声音。截图比较则限定相同测试环境，不要求不同 GPU 的最终像素完全相等。

---

## 最后收束成一个明确判断

**你现在最值得做的，不是“增加一个 Experience Runtime”，而是改变现有代码的控制关系。**

从：

```text
章节拥有进度
章节决定镜头
镜头决定物体状态
各层自己决定何时更新
```

变成：

```text
故事定义状态
运行时统一采样
场景绑定执行
相机负责构图
DOM 与 WebGL 共享配准
声音消费同一状态和明确事件
```

我会把第一轮的目标定为：

> **在 About → Life → Frame 这段里，直接进入任意位置，都能看到正确的房间后果、唯一且连续的照片，以及与最终相机同帧对齐的内容。**

这段成立后，再把同样的机制扩展到显示器、抽屉、项目档案和 Contact。届时你优化的就不再是几段互相衔接的动画，而是一套可以持续精修的空间叙事系统。
